# Spotify provider discovery and quota lifecycle

Reconciliation now separates successful catalog discovery from candidate acceptance. Migration 31 adds `spotify_discovery(fingerprint, response_json, completed_at)` and `provider_cooldown(provider, until_epoch)`. Existing Track candidate snapshots, established Album programs, trusted identities and manual exclusions keep their separate ownership.

The Spotify adapter attaches an independent Library connection before worker construction. Successful typed catalog GET responses are persisted and replayed through the same translation and evaluator code. Empty pages are successful discovery too. Album detail and bounded program pages are reusable independently, including rejected competitors. This stores requested bounded responses, not an enumerated Spotify catalog. Expired records are removed incrementally (at most 32 per successful write), using an age index. Refresh failures never write a replacement response or clear the previous successful record.

## Exact discovery keys

A fingerprint is a deterministic, unhashed request key: `spotify:<SEARCH_STRATEGY_VERSION>:<complete catalog URL>`. It includes the provider endpoint/base URL, market and all actual query parameters, including endpoint scope, query text, limit and offset. No credentials or bearer token appear in it. Canonical Album IDs group batch work; identical resulting provider queries can share a result even across distinct canonical entities without merging those entities.

Album query generation uses the existing Album title variants, presentation/typography normalization and the resolved Spotify Artist search name(s). One shared Artist name permits an Artist-qualified query; multiple different names produce the existing Album-only query. Equivalent Artist IDs continue to filter/evaluate the returned page locally. An empty full-title query can perform the existing single distinctive-token fallback. Both queries are cached separately.

Track query generation uses presentation/typography-normalized Track title and the structured primary Artist search name. A uniquely known Spotify Artist supplies its observed provider name. Album title, positions, duration, date, program size and canonical evidence affect evaluation, **not this Track query**. An explicit diagnostic Artist lookup name changes the query without changing canonical metadata. Observed Spotify Artist names also persist with market/version/Artist-ID keys, so establishing Artist identity or restarting does not introduce a new detail request for a name already discovered.

`SEARCH_STRATEGY_VERSION = 1` covers candidate discovery only. `EVALUATION_VERSION = 5` remains independent. Query construction, endpoint breadth or pagination changes require a discovery version change; acceptance-rule changes normally require only evaluator version changes. Cached pages/programs pass through current confidence rules; these rules were not loosened.

Title and query-relevant Artist changes naturally produce different keys. Genre, file paths, source availability, display-only fields and evaluation-only MusicBrainz evidence do not. Artist equivalence invalidates discovery only when it changes the actual query; acceptance-only changes reuse the same responses.

## Freshness, explicit actions and quota

`DISCOVERY_TTL_SECONDS` centralizes the v1 **30-day** lifetime for all successful responses, positive and negative. Expiration permits a later explicit/bounded refresh; it does not schedule HTTP. Normal browsing, Connections sorting/filtering/scrolling, Metadata and opening diagnostics remain provider-free. Opening a diagnostic preloads current-query candidates through a cache-only adapter path; misses, changed market/inputs and expiry cannot authenticate or make HTTP requests. This path needs only the configured market, not credentials. A diagnostic's ordinary Track search reuses fresh results and reports when no requests were needed. `spotify_discovery_status` exposes never-searched/fresh/expired state, completion time, raw candidate count, unfetched-page indication and cooldown remaining for an exact key. Missing current keys mean discovery is required; user exclusions remain separately typed durable state.

Routine Album re-evaluation reuses discovery. Explicit **Search Spotify again** actions for Track and Album bypass TTL, respect cooldown and retain old successful results on failure. An Album refresh is scoped to that Album's worker command rather than allowing refresh mode to leak to another context. **Check Spotify again** only clears a manual exclusion and restores eligibility; the separate refresh action requests new provider discovery.

Every catalog response, including token responses, captures 429 `Retry-After` centrally. Delta seconds and HTTP dates are supported. The provider-wide deadline persists across workers and restart; missing/invalid headers use the existing conservative 30-second fallback. Requests check fresh cached responses before checking cooldown, and cooldown before token acquisition. The matcher scheduler no longer caps 429 Retry-After at 120 seconds. A 5893-second header retains the actual deadline and reports approximately 1h 38m plus the exact seconds. Neither quota errors nor authentication/access/network/timeout/5xx/malformed failures become negative provider knowledge.

The batch callback stops the remaining Album batch on deferred provider failure, including program-fetch failures. The failed Album remains subject to the existing deferred-work/cooldown policy. Remaining Album/Track work is not queried and the cursor is not advanced past it. Local Track/program re-evaluation remains available during cooldown.

Manual **Not on Spotify** is stronger than provider caching. Version changes, expiry and Retry unresolved cannot clear it. Only Check Spotify again or an existing explicit trusted connection changes this state. Nothing here changes membership, canonical entity identity, playback precedence or playlist ordering.

## Album and Track request policy

Retry unresolved first runs bounded stale local evaluation on the existing review worker, then its completion callback plans at most 20 canonical Albums using the existing keyset cursor. Each Album completes before advancing. Fresh Album discovery is replayed through the adapter and current evaluator. A completed negative Album result remains shared by its entire reconciliation context.

The former batch policy then automatically searched **every** unresolved Track, cursor-paging until exhaustion. That fan-out was removed. After an Album absence or rejection, its Tracks remain unresolved. Individual Track search and local-first playback's existing bounded Track resolution still work and can discover occurrences on another release. They use their own persisted query results. The core Track-fallback cursor helper remains available for explicit policies, but batch Retry unresolved no longer invokes it.

Multiple returned candidates and provider `next`/offset information remain cached. Incomplete discovery is not represented as an exhausted candidate set. Existing Album program pagination stays bounded at 20 pages/1000 entries; no page 1 is fetched again while its result is fresh. A new UI flow to fetch additional search pages is intentionally deferred; the current diagnostic continues to disclose that further results exist and permits explicit candidate inspection/connection and fresh searching.

## Validation and quota measurements

All provider validation used local mock servers, controlled time and disposable databases; **live Spotify requests: 0**.

* Generic catalog-only 150-Track absent Album: four complete matcher invocations. With persistence disabled, four Album searches; with persistence enabled, one. The three repeated runs fall from **3 Album searches to 0**. First-run Artist discovery is unchanged. There are no batch Track queries after Album failure. The former fan-out could add 150 Track searches per pass; that is a policy-path count, not a live quota measurement.
* Exact Album lookup repeated 450 times and then restarted: **0 additional token/API requests** after the successful discovery. Observed request categories confirm one Album search. The adapter retains the last 64 actual catalog request audits (category, exact fingerprint, and explicit-refresh/expired/no-completed-result reason), with no production logging.
* Disposable real Library snapshot: `Cellular Music` has 150 saved Tracks, no old candidate/program cache and no manual exclusion in this historical snapshot. Its actual canonical context was reconciled against an absent-Album **mock** response. The first run made four mock HTTP calls (token, Artist discovery, full-title Album search, token-fallback Album search); each of three subsequent runs made **0**. No name/title is special-cased in production.
* 429 with Retry-After 5893: 150 subsequent candidate contexts make **0 further requests**. A cached successful page remains replayable, including across restart. Controlled-time tests verify eligibility exactly at the deadline and TTL expiry without sleeps.
* Refresh 401, 403, 429, 5xx, network and malformed-response tests preserve previous successful candidates. A real local-HTTP timeout during catalog token refresh also preserves the previous successful page; existing timeout/error-classification tests remain in place. Empty successful Track pages now replay locally after evaluator-version changes rather than becoming needs-retry solely because the page is empty.
* Three persisted Album candidates and a fetched program survive a simulated historical evaluator rejection. The current canonical evaluator accepts one and persists its Album association with **0 additional HTTP calls**. A separate three-Track-candidate fixture verifies actual persisted evaluator-version bookkeeping and association after restart, entirely locally.
* Existing canonical evidence, Artist equivalence, untitled normalization, competition/program ambiguity, source/membership preservation and targeted Connections tests remain applicable.

On a disposable copy with 200,000 Tracks (debug build), opening/migration measured 14 ms. Connections pages measured 13–28 ms; indexed stale scan p50/p95 1.8/2.3 ms; bounded 32-Track local work 3.4/4.0 ms. A separate cache table populated with 200,000 deterministic successful query records measured lookup p50/p95 **22/34 µs**, using `sqlite_autoindex_spotify_discovery_1`. An eight-candidate local acceptance replay within a 32-Track batch took 74 ms. These are observations, not new product budgets. `examples/spotify_discovery_performance.rs` reproduces the indexed cache measurement on a disposable database.

Legacy successful searches cannot be reconstructed when previous versions saved no candidates. The first subsequent eligible reconciliation must discover those contexts once. Cross-process simultaneous cache-miss coalescing and a richer per-Album freshness UI are deferred; canonical grouping plus persisted exact-query reuse deduplicate the application's sequential batch. Standalone adapter clients opt into persistence with `with_library`; reconciliation workers in the application do so automatically.
